# 简历整理

把简历里的信息整理成「类-实例-属性」结构的 Markdown 简历文件夹。产物是**数据**，不是简历本身：这个文件夹之后可以被「招聘表单填写」这类技能直接消费，也可以直接给人看。

## 先读规格

- `references/resume-folder-spec.md`：简历文件夹的结构契约（类的组织、三态值、附件路径、收工核对）。动手前先读它。
- **模板目录**：13 个类的模板都在这里。每个类目录里有 `README.md`（这一类记什么、实例怎么命名、注意事项与降级策略、没有对应栏目时填哪）和 `模板.md`（属性规范，一行一条：属性名、形态、必填性、取值、说明）。位置固定：本技能目录下的 `resumeTemplate/`。没有模板时问用户，不要凭印象自己造一份类结构。把这个目录整体复制到目标位置，实例照该类 `模板.md` 逐条写。

## 输入

- 一个或多个 PDF / Word 简历；多份合并进同一个简历文件夹。
- 优先读 PDF 文本层；文本层为空（扫描件）时用 OCR 或视觉能力读取；两者都没有时，请用户提供可复制的文本。
- 输入文件只读，不改写简历原文。

## 硬规则

1. **填任何一个类之前，先读这个类的 `README.md` 和 `模板.md`。** 两者合起来回答的是：这个类有哪些属性、每个属性是「必填」还是「可空缺」、带条件的属性在哪些实例上可以空缺、实例怎么命名、值拿不到时降级到哪。不读就填，等于凭印象写，必然漏项。
2. **只新建、不合并。** 已有目录不动，不覆盖已有值。
3. **只落简历原文的事实。** 不改写、不推测、不补全。
4. **每个类都要有交代**：要么有实例文件，要么在简历文件夹的根 `README.md` 的「已确认没有的项」里记一行。两者都没有就是漏了一整个类。
5. **类 README 的 `## 必备实例` 必须逐个落实**：简历里没有的（例如教育经历里的高中段），要列进缺项清单，不能因为简历没写就静默跳过。

6. **临时文件一律写在工作区根目录下的 `temp/`**：报告、截图、导出这类中间产物只写到这里（目录不存在就创建），不写进简历文件夹，也不写进技能包目录、不散落在工作区根目录。

## 目标目录

**只新建、不合并。** 目标目录必须不存在或为空；已存在且非空时停下，请用户换一个空目录，不要写入、不要覆盖已有内容。

**简历文件夹固定是工作区根目录下的 `generated-resume/`**（名字固定，不做搜索、不改名）。工作区根目录就是当前工作目录；用户明确指定了别处时按用户的来。

**不要建在技能包目录里**——技能包可以整体搬走、可以分享给别人，个人数据一律留在工作区。

附件属性的值一律写成「相对工作区根目录的路径」。

生成出来的简历文件夹固定是这个形状（权威定义在 `references/resume-folder-spec.md` 的「目录布局」，这里只是速览）：

```text
<工作区>/generated-resume/
├── README.md               # 库说明：结构、三态、附件路径、类清单、已确认没有的项
└── <类名>/                  # 一个类一个目录，类名就是目录名
    ├── README.md           # 这一类记什么、实例怎么命名、注意事项与降级策略、填写位置
    ├── 模板.md              # 属性规范：一行一条，属性名、形态、必填性、取值、说明
    ├── <实例>.md            # 实例数据，一个实体一个文件
    └── <附件文件>            # 附件（证件照、成绩单、证明等）与实例同级
```

## 流程

1. **建类的清单**：读完简历，先列出有哪些类、每类几个实例、每个实例叫什么名字。
2. **铺骨架**：把 `resumeTemplate/` 复制到目标位置（含根 `README.md`）。产出里只该有：根 `README.md`、类 `README.md`、类 `模板.md`、实例文件与附件。**不要生成"骨架""缺口清单"这类中间文件**，实例直接照类 `模板.md` 逐条写。
3. **逐类填值**：每换一个类，先读该类的 `README.md` 与 `模板.md`，再按 `模板.md` 的清单逐条落值；`必填` 的属性一条都不能少，`可空缺` 的属性可以整行不写。
4. **核对类的覆盖**：逐类确认"有实例"还是"用户确认没有"。没有实例的类，要在简历文件夹的根 `README.md` 的「已确认没有的项」里记一行；同时把 `## 必备实例` 里的每一项单独落实——**简历里没有的必须列进缺项清单**，不能默认不存在。
5. **列缺口**：简历里没有的属性值，先判断它是「不适用」还是「待补」。带条件的属性（`必填；某某可空缺`）要逐实例判断：适用的必须有值，不适用的写 `〔不适用〕原因`。这些先攒进缺项清单，不要现在就发给用户。
6. **处理附件**：把缺的文件、命名规则与目标目录也写进同一份清单，同样先不单独发。
7. **自检扫描**：按下面「自检扫描」把整份库从头过一遍，扫出来的缺口并进同一份清单。
8. **一次性交清单**：整份库填完、扫完之后，才把这份清单发给用户；同一份内容同时写进工作区根目录下 `temp/` 里的报告文件（见「缺项清单与报告」）。

## 抽取纪律

- 只落简历原文里的事实。不改写、不润色、不推测、不补全数字与日期。
- 数值、日期、专有名词按原文照抄，不要"顺手"纠正拼写或统一格式。
- 一条信息归到哪一类，按类 `模板.md` 的属性清单与类 README 的「注意事项与降级」判断，不要按简历上的栏目名机械对应。
- 多份简历同一个属性取值冲突时不要自行取舍，列进缺项清单让用户裁决。

## 三态与收工

每个属性都必须落成三态之一：

- `- 属性：值` —— 已知。
- `- 属性：〔不适用〕原因` —— 结构上不适用（例如还在读的学历段没有毕业证书、用户明确说不提供的证明人）。要写明原因。
- `- 属性：待补（缺什么）` —— 简历里没有、用户还没回答、或附件还没到位。

「待补」只是运行中的中间态，不写进类的 `模板.md`：`模板.md` 只回答每个属性是「必填」还是「可空缺」，值层面的三态由实例文件承担。

**收工条件是：自检扫描后缺口清零**——缺项 0、待补 0、未交代的类 0、必备实例 0。只有「不适用」和「条件项已逐实例确认」不算缺口。不要为了让检查通过，把「待补」改写成「不适用」。

## 已确认没有的项

用户确认"这个完全没有"时，不要建一个全是「不适用」的空实例，而是在**简历文件夹的根 `README.md`** 的「已确认没有的项」小节里记一行，例如：

```markdown
## 已确认没有的项

- 校内活动和社会实践：用户确认没有校内任职与社会实践经历
- 教育经历 · 高中段：用户确认不提供（走社招，不用从高中填起）
```

自检扫描时以这里为准：记过的项就不再当缺口。只记用户明确确认过的结论。

## 附件

- 附件属性的值是路径，不写文件内容。需要哪些文件、每个文件怎么命名、放到哪个目录（目录用相对工作区根目录的写法），都写进缺项清单，等整份库扫完一起交给用户。
- 用户把文件放好之前，这个属性保持 `待补`；放好之后改写成路径。
- 不要从简历里猜测图片用途，也不要自己截图当附件。

## 自检扫描（必做）

填完一个类就先扫它一遍，全库填完后再整体扫一遍。扫描随时可做，但清单只在整份库填完之后一次交给用户。**这一步完全靠模型判断**：某条属性"该不该有值"取决于这个人的实际情况，光看字段规则判不出来。

逐个类做这四件事：

1. **读规则**：重读该类的 `模板.md` 与 `README.md`——必填/可空缺、带条件的例外、降级去向、实例命名。
2. **看数据**：读该类每个实例，逐条属性对照规则——必填项有没有交代；**可空缺项在这个用户身上该不该有值**。例如简历里有六级成绩，`外语能力/` 的证书子表就不该是空的；简历里写了技术栈，`实习经历/` 的「技术栈与方向」就不该空着。这类"该有而没有"只有对着用户数据才看得出来。
3. **点实例**：这个类该有哪几段（含 `## 必备实例` 声明的）——是漏抽了，还是用户确实没有（后者要在根 `README.md` 的「已确认没有的项」里有记录）。
4. **对附件**：逐条看附件类属性——库里指的文件在不在、命名和目录对不对。

## 缺项清单与报告

缺什么、怎么交给用户、答案落到哪，都走同一份清单，不要一个字段一条消息。

**一行一个实例，按类分组：**

```text
<类>/<实例>.md：<要补的属性1>、<要补的属性2>……；附件：<附件名> → 放到 <目标目录>
```

- 附件写清"放到哪个目录"，路径用相对工作区根目录的写法。
- 一个实例缺得多就多写几行，不要为了压成一行而省略；整类的问题单独一行，例如"这一类一个实例都没有，请确认是没有还是漏了"。
- 每条都要说清缺什么、要什么格式：格式写在属性后面的括号里，例如 `证件有效期（YYYY.MM.DD-YYYY.MM.DD）`；为什么要这一项不显然时，再补一句人话。
- 例子一律用占位示例，不要拿用户的真实数据当例子。例如：

```text
个人信息/张三.md：姓名拼音、证件号码、证件有效期（YYYY.MM.DD-YYYY.MM.DD）、紧急联系人姓名/关系/电话
个人信息/张三.md：附件：身份证人像、身份证国徽、证件照、生活照 → 放到 generated-resume/个人信息/
教育经历/：缺高中段，请给学校名和起止时间（应届/校招必填；确实不需要就说一声，我记到根 README 的「已确认没有的项」里）
校内活动和社会实践/：这一类一个实例都没有，请确认是没有，还是漏了
```

**纪律：**

- **整份库填完、扫完之后才发清单**：不要填到一半就发一条，一轮只发一条，把该问的一次问完。
- 用户答完，把答案落进库里，再扫一遍；还有缺口就发一条新的（比上一条短），不是重问同一件事。
- 用户答"没有""不适用"就落 `〔不适用〕原因`，答了值就落值；不要替用户编造，也不要把"大概是这样"当答案。
- 已经答过的、确认过不适用或没有的，不再问。
- 每一项都要能落回属性行：用户答完就把 `待补` 改成值或 `〔不适用〕原因`。

**落点：** 清单直接贴在对话里，同时写进工作区根目录下 `temp/` 里的报告文件（文件名带日期；目录不存在就创建）；**不要另外维护第二份"缺口文件"**。报告在清单之外再补三行说明：

- 输入了哪些简历文件；
- 生成了哪些类和实例；
- 哪些属性标了「不适用」，理由是什么。

## 通用性

- 不把某个 harness 的工具名、目录名或某个用户的个人信息写进简历文件夹。
- 生成的库要交给「招聘表单填写」这类 skill 消费时，只需简历文件夹本身（工作区根目录下的 `generated-resume/`）即可。

## 不要做的事

- 不修改用户的原始简历文件。
- 不合并进已有简历文件夹，不覆盖已有值。
- 不把简历里没有的信息当成已知事实，宁可留在缺项清单。
- 不把临时产物写进简历文件夹或技能包目录；临时文件一律写到工作区根目录下的 `temp/`。
